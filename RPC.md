# RPC and node lookup (steps 4–5)

The node uses `Network` for RPCs. `Network` uses the `Transport` interface,
implemented by `UDPTransport` and `SimulatedTransport`. Both environments
therefore exercise the same message encoding, response matching and retry code.

## Starting a node

Call `Listen(ip, port)` to bind UDP, then pass the returned transport to
`NewKademliaWithTransport(transport, config)`. Port 0 selects a free local port.
The node's ID uses the actual bound address.

For simulations, obtain the transport from `SimulatedNetwork.Listen(address)`
instead. `NewKademlia(address, config)` alone still creates an offline node.

`NewKademliaWithTransport` starts RPC reception and owns the supplied transport
on success; callers must not independently read packets from that transport.
If construction fails, the caller remains responsible for closing it.
Call `node.Close()` to release the transport and stop its receiver.

Use `node.Ping(ctx, &peer)` to send a PING. The peer contact must contain its
canonical address and the SHA-256 ID derived from that address.

## Messages and response matching

Messages use JSON with a request ID, RPC type, response flag, sender contact,
and an RPC-specific payload.

Each logical call receives a 128-bit request ID generated by `crypto/rand`.
Replies must match an active request's ID, RPC type, source address and node ID.
The sender's advertised address must also match the packet's observed source.
Invalid, unmatched, duplicate and late replies do not complete unrelated calls.

This protects against plausible replies guessed by an attacker who cannot
observe the request. It does not authenticate traffic against an on-path
attacker. Source-address validation assumes direct addressing, as in the
intended container network; NAT address translation is not implemented.

## Timeout and retry policy

- Default timeout: 2 seconds per attempt.
- Default retries: 2 additional attempts (3 total).
- Retry only after timeout; a local send error fails immediately.
- Reuse the same request ID and encoded request for retries of one call.
- Caller cancellation or node shutdown interrupts the wait.
- Remove pending request state on success or any failure.
- Report `ErrRPCTimeout` after the last unanswered attempt.
- Report PING elapsed time for the whole call, including retry waits.

PING and FIND_NODE are safe to repeat. There is no server-side response cache.
Later state-changing RPC handlers must also account for retries.

## FIND_NODE and iterative lookup

`SendFindContactMessage(ctx, peer, targetID)` asks one peer for up to K contacts
closest to an arbitrary 256-bit target. The target need not identify an existing
node. The recipient searches its local routing table, excludes the requester,
and sends a list; it does not forward the request or perform its own lookup.

`LookupContact(ctx, targetID)` performs the distributed search:

1. Copy known contacts into a candidate set keyed by ID.
2. Sort non-failed candidates by XOR distance and take the closest K.
3. Query up to Alpha unqueried candidates concurrently.
4. Wait for the whole batch to complete or time out.
5. Mark replies/failures, merge newly discovered contacts, and repeat.
6. Finish once all of the current closest K non-failed candidates have replied,
   or all available candidates have been exhausted.

This is the strict-parallelism option described by the lab's
[Kademlia reference](https://xlattice.sourceforge.net/components/protocol/kademlia/specs.html).
A round without improvement does not skip the remaining nearest candidates.
An exact target match also does not stop collection of the remaining contacts.
Farther candidates are kept as replacements when closer peers fail.
Each peer is queried once per lookup, apart from RPC-level retransmissions.

Returned contacts are sorted, distinct, responsive peers; the initiating node
is excluded. At most K contacts are returned, with fewer allowed in a small or
partially reachable network. They are the closest discovered responsive peers,
not a guarantee of the global closest peers under arbitrary connectivity.

Contact addresses and address-derived IDs are validated. Invalid responses
fail that probe. Duplicates and references to the initiating node are ignored.
If no usable peers are known or none respond, lookup returns
`ErrNoReachableContacts`. Cancellation and shutdown return their corresponding
errors without partial results.

Successful probes update the local routing table using its current basic
insertion policy. Network-wide communication-driven maintenance, eviction,
refresh and joining are still step 6.

## Seeding a lookup before joining is implemented

Given already-running nodes and a parsed target ID:

```go
if err := node.AddContact(bootstrap.Contact()); err != nil {
    return err
}
contacts, err := node.LookupContact(ctx, targetID)
```

`AddContact` validates the seed but does not check its liveness or join a network.
The bootstrap node needs appropriate contacts in its own routing table for
lookup to discover additional nodes.

## Routing-table changes

The flat array of 256 buckets is retained. A read/write mutex protects table
access; insertion and results copy contact IDs so callers cannot mutate stored
state. Self contacts are ignored.

Nearest-contact selection scans all buckets and sorts the result. The starter's
early-stop traversal could miss closer contacts because bucket adjacency around
the local node is not distance order around the lookup target.

## Verification and current scope

Run `CGO_ENABLED=1 go test -race -count=1 ./...` with Go and a C compiler.

Tests cover PING and lookup over simulated and loopback UDP transports,
1,000-node lookup against a global nearest-contact oracle, multi-hop discovery,
strict parallel batches, failure fallback, duplicate contacts, termination,
cancellation, concurrent lookups, and RPC response validation. Routing tables
are manually seeded in these tests; they do not test joining yet.

FIND_VALUE, STORE, full routing maintenance, joining, periodic tasks, lookup
event logging, experiments and the CLI remain for their planned steps.
